手上这台小天才 Z3（msm8909w，Android 7.1.1）早就通过 9008 覆写分区拿到了 Magisk Root，但系统一直有些莫名其妙的问题。一直以来最烦人的一条：QQ 手表版连上 WLAN 之后，界面始终显示「没连上网」，包括使用腕上哔哩也是一样，有一次莫名其妙掐网害得我被迫在公交站无聊了1个小时。

这台表本来就没插 SIM 卡，WiFi 是它唯一的联网方式，QQ 连不上基本没有更多使用价值了（其实是在学校作为手机的平替） 。于是有了这次排查。

> 前提说明：设备是我自己持有的，Root具体教程可以参照B站，本文只涉及自己设备上的分析与修改。涉及厂商框架逆向的部分仅用于理解自己设备的行为。

## 先说结论

- QQ「没联网」和 IP、DNS、防火墙、路由统统无关，网络栈从头到尾都是通的
- 真凶是厂商打进 framework 的 **ovum 框架**：一个跑在 system_server 里的「进程自启动许可证」系统，QQ 的后台网络进程 `com.tencent.qqlite:MSF` 拿不到许可证，起不来
- 每应用白名单放在桌面的 `watch_boot_start.xml` 里，总开关是属性 `persist.sys.selfstart.open`
- `setprop persist.sys.selfstart.open 1` 一条命令根治，进程管控整体关闭
- 顺手把 13 个厂商云控组件全部 `pm disable-user`（可逆），遥测和云端常驻连接全部消失

## 排查环境

不知道是不是我的问题，Z3的 USB 口和线材一直不太稳定，运行adb root必死，adbd 还会莫名挂掉，中途 PC 的 USB 控制器都被卡死过一次。所以第一步就是切到无线：

```bash
adb connect 192.168.10.33:5555
su -c "setprop persist.service.adb.tcp.port 5555"
```

之后所有操作都走 WiFi ADB，跟不稳定的 USB 彻底拜拜。

设备基本信息：

```text
ro.product.model = XTC_Z3
ro.build.version.release = 7.1.1 (SDK 25)
ro.board.platform = msm8909
ro.build.date = 2019-12-19
SELinux = Enforcing
root = Magisk 20.4 (/sbin/su -> magisk)
```

系统应用清一色的 `com.xtc.*` 前缀，还有一堆厂商定制包，具体清单后面贴。

## 第一步：把系统侧的嫌疑全部排除

先按套路把网络层查了个遍，全部干净：

- `ping 223.5.5.5` 通，延迟正常
- `ping www.baidu.com` 正常解析，说明 DNS 没问题
- 连 QQ 自己的 `msfwifi.3g.qq.com` 都能解析
- `iptables -L -n` 全是标准规则，没有针对任何 uid 的 DROP
- `ip rule` 是 Android 7.1 的标准策略路由，没有 per-uid 劫持
- `/system/etc/hosts` 只有 localhost
- `dumpsys connectivity` 显示 WLAN 状态 `CONNECTED/VALIDATED`——系统自己都认为网络是好的
- QQ 的 uid（10055）在 netpolicy、appops 里没有任何限制

系统侧排查的结论是：**内核和框架层面，QQ 的网络应该畅通无阻**。那问题只可能在 QQ 进程自己身上。

## 第二步：logcat 抓到关键一行

启动 QQ 并全程盯日志：

```bash
logcat -c
monkey -p com.tencent.qqlite -c android.intent.category.LAUNCHER 1
```

抓到一行非常可疑的日志：

```text
D ovum_SelfStartManager: com.tencent.qqlite have no selfstart permission to startProcess
```

`ovum_SelfStartManager`——厂商框架里管「应用能不能启动进程」的东西。更实锤的是 `ps` 里根本没有 QQ 进程：ActivityManager 收到了启动请求，但进程被这个管理器拒了。

也就是说：**QQ 不是连不上网，是压根没被允许「出生」**。之前偶发能看到 QQ 界面，是因为前台 Activity 有临时豁免（后来反编译证实了有 `mTempAllowSet` 机制），但后台的 MSF 长连接进程每次都被拦，QQ 于是永远显示「没联网」。

## 第三步：把 ovum 挖出来反编译

日志 tag 的字符串不在 services.odex 里，全盘搜文本定位到实现所在：

```bash
grep -rl "selfstart permission" /system/framework /system/app
# /system/framework/arm/boot-framework.oat
```

拉下 boot-framework.oat（36MB），在里面搜 `dex\n` 魔数，找到两个嵌入式 dex，修好校验和后用 jadx 反编译。因为 odex 是 quickened 指令，jadx 大量方法解码失败，但**字符串常量池里的关键情报全在**：

```java
public class SelfStartManager {
    private static final String CONTEXT_PACKAGE = "com.xtc.i3launcher";
    private static String ENABLE_PROP_KEY = "persist.sys.selfstart.open";
    private static final String PERMISSION_PREFERENCE = "watch_boot_start";
    private static final String PREF_ACTION = "com.xtc.selfstart.PREF_CHANGE_ACTION";
}
```

三个关键信息一次到手：

- 总开关属性：`persist.sys.selfstart.open`
- 每应用白名单：名为 `watch_boot_start` 的 SharedPreferences，上下文包是桌面 `com.xtc.i3launcher`
- 白名单变更广播：`com.xtc.selfstart.PREF_CHANGE_ACTION`，framework 收到后重读文件

反编译还能看到硬编码放行列表只有 7 个 XTC 系应用加输入法，以及临时放行、休眠状态、按 uid 算流量等一堆配套逻辑——这是一套完整的「哪些应用允许在后台活着」的许可证系统。

## 第四步：两种修法，一个临时一个根治

**临时修法**（改白名单）：白名单文件在桌面应用的数据目录里，里面 30 个包全是 XTC 自家的，连厂商定制版网易云音乐都在，QQ 自然不在：

```bash
su -c "sed -i 's|</map>|    <boolean name=\"com.tencent.qqlite\" value=\"true\" />\n</map>|' \
  /data/data/com.xtc.i3launcher/shared_prefs/watch_boot_start.xml"
am broadcast -a com.xtc.selfstart.PREF_CHANGE_ACTION
```

改完日志立刻变脸：

```text
D ovum_SelfStartManager: com.tencent.qqlite hava selfstart permission to startProcess
D MSF.D.Proxy: bind com.tencent.mobileqq.msf.service.MsfService service finished true
```

MSF 绑定成功，扫码登录的二维码也能加载出来了。

但这有个隐患：这个文件由桌面管理，**开机时它会从云端同步覆盖回来**，实测重启后 QQ 条目果然被刷掉了。

**根治修法**（总开关）：既然反编译拿到了 `ENABLE_PROP_KEY`，直接把开关设上：

```bash
su -c "setprop persist.sys.selfstart.open 1"
```

persist 属性自动持久化，重启不丢。重启后日志变成了更有意思的一行：

```text
D ovum_SelfStartManager: selfstart disable,allow:com.tencent.qqlite
```

`selfstart disable`——整个许可证系统被关闭，所有应用放行。此后无论白名单被云同步刷成什么样都不再重要。QQ 主进程和 `:MSF` 后台进程双双常驻，二维码登录、收发消息全部正常。

## 第五步：云控全家桶，逐个点名

QQ 修好后顺手把云控清了。这台表上的厂商组件盘点下来一大串，策略是**只禁 `/system` 下的厂商组件，`/data` 下自己后来装的管理工具一个不碰**（脚本里加了安装路径校验，防止误伤）：

```bash
pm disable-user --user 0 com.xtc.systemagent    # 遥测/大数据
pm disable-user --user 0 com.xtc.appupdate      # 云端应用更新
pm disable-user --user 0 com.xtc.dialstore      # 表盘商店
pm disable-user --user 0 com.xtc.personalitydress # 装扮商店
pm disable-user --user 0 com.xtc.moment         # 朋友圈
pm disable-user --user 0 com.xtc.weichat        # 微聊
pm disable-user --user 0 com.xtc.grade          # 等级
pm disable-user --user 0 com.xtc.motion         # 运动云同步
pm disable-user --user 0 com.xtc.weather        # 天气（云端源）
pm disable-user --user 0 com.xtc.bleaddfriend   # 加好友
pm disable-user --user 0 com.xtc.selftest       # 自检
pm disable-user --user 0 com.xtc.thirdappmanager # 第三方应用管理
pm disable-user --user 0 com.xtc.message        # 短信（没插SIM卡）
```

全程用 `disable-user` 而不是卸载，一条 `pm enable` 就能整体回滚。

重启后验证：

- 13 个进程全部不再出现
- 原先 system uid 到云端的一条常驻 TCP 连接（遥测通道）消失
- 桌面、设置、闹钟、输入法正常保留，自己装的工具全部健在

## 顺带踩过的坑

### odex 里的 dex 不是躺在明面上的

7.1 的 boot.oat 里 dex 是嵌在 ELF 结构中的，直接按魔数扫描能找到，但校验和是坏的（quickened 处理过），jadx 要加参数跳过校验。即便如此部分方法仍因 quickened 指令解码失败，好在**字符串常量池不受影响**，逆向这种厂商框架时，常量（属性名、文件名、广播 action、tag）往往就够用了。

## 收获

1. **「应用显示没网」不一定是网络问题**。当系统侧全部证据（防火墙、路由、DNS、验证状态）都干净时，要往「应用进程本身是否健康」去查，logcat 里一行 `have no selfstart permission` 比任何网络诊断都值钱
2. **厂商云控的最强形态不是拦截流量，而是控制进程生死**。流量可以翻墙绕，进程不让出生连翻墙的机会都没有
3. **逆向厂商框架不需要完整反编译**。quickened odex 解不动没关系，属性名 + 文件名 + 广播 action 这三样常量就是全部攻击面
4. **`disable-user` 是解散全家桶的正确姿势**：可逆、不动数据、不破坏 OTA 结构，比 rm 强太多
5. 神人厂商设备的「神秘问题」多半是云控逻辑在作怪——你的设备连着人家的服务器，人家随时能改你设备的行为，这次白名单被云端刷回去就是现场直播

## 回滚方式

```bash
# 恢复全部 13 个组件
for p in systemagent appupdate dialstore personalitydress moment weichat grade motion weather bleaddfriend selftest thirdappmanager message; do
  adb shell "su -c 'pm enable com.xtc.$p'"
done
# 恢复进程管控
adb shell "su -c 'setprop persist.sys.selfstart.open 0'"
```
