这是一台从拼多多买的杂牌 Android MP3，型号标着 BF10，芯片是 MT6735M，系统是 Android 7.0。它本来只能听歌；本人同学想装个阅读器看小说，结果发现第三方 APK 根本装不进去，于是有了这次折腾。

目标是在不刷第三方固件、不弄丢原系统的前提下，装上第三方应用并拿到 Root。最后的结果是 **Magisk v26.4 永久 Root + 第三方安装限制解除**，原厂 boot/system 完整备份。

> 风险声明：本文仅针对我本人持有的设备。设备无官方固件、无 recovery，任何分区写入都可能导致不可恢复的损坏。下面的 exploit/testkey 细节仅用于同型号设备自查，不要用于他人设备。

## TL;DR

- 这台拼多多买的“MP3”其实是 **MT6735M + Android 7.0** 的杂牌 Android 播放器；本来只能听歌，本人同学想装阅读器看小说。存储是 **7.3GB eMMC**，不是 SD 卡。
- 装不了第三方应用，不是存储坏了，而是厂商在 `PackageManagerShellCommand.runInstall` 里加了自定义安装限制：
  - 读 `persist.sys.install.by.pwd`
  - 值为 `0` 时直接放弃安装会话 → `INSTALL_FAILED_INVALID_INSTALL_LOCATION`
  - 非 `0` 时提交安装
  - 同时还有一个 `ignore_app` 白名单和一个 system uid 的 `bs.android.systemcontrol` 管理应用
- 临时 root 用 **mtk-su（CVE-2020-0069）**，拿到 `uid=0`，先把 boot/system/关键分区完整备份。
- 永久 root 用 **Magisk v26.4** 打 boot 补丁。
- 这台 MTK LK 的 fastboot 不能直接处理 16MB 的整分区 boot 镜像，会在发送阶段 `no link`；把尾部 AVB/填充去掉，用 **8.9MB trimmed 镜像**后一次刷入成功。
- 最终 `adb shell su -c id` 返回 `uid=0(root) ... context=u:r:magisk:s0`，`magisk -v` 为 `26.4:MAGISK:R`。

## 1. 设备侦察：它到底是个什么东西

ADB 连上后，先看基本身份：

```bash
adb shell getprop | grep -E 'ro.product|ro.build|ro.secure|ro.debuggable|verifiedboot'
```

关键结果：

```text
ro.product.manufacturer = alps
ro.product.model = BF10
ro.product.cpu.abi = arm64-v8a (also armeabi-v7a)
ro.build.version.release = 7.0
ro.build.version.sdk = 24
ro.build.version.security_patch = 2019-05-05
ro.hardware = mt6735
ro.board.platform = mt6735m
ro.boot.verifiedbootstate = orange
ro.boot.flash.locked = 0
SELinux = Permissive
build date = 2025-10 (system is still Android 7)
```

几个第一印象：

1. **我一开始以为是 arm32**：ABI 列表其实是 `arm64-v8a, armeabi-v7a, armeabi`，内核 `aarch64`。所以后面 mtk-su 用的是 arm64 版本。
2. **我一度怀疑“唯一存储是 SD 卡”**：因为 `pm install` 一直报 `INSTALL_FAILED_INVALID_INSTALL_LOCATION`，很容易把方向带到安装位置/存储卷上；但 `/proc/partitions` 里只有 `mmcblk0`，设备名 `QN16BB`，还有 `mmcblk0boot0/boot1/rpmb`。这是 **eMMC**，不是 SD。没有 `mmcblk1`。真把 eMMC 当 SD 拔了就出大事了。
3. **Bootloader 是我自己解锁的**：`verifiedbootstate=orange`、`flash.locked=0`；之前我用 fastboot 的 OEM 指令解了 BL，所以有可用 fastboot 的底子。后来 16MB 镜像把 fastboot 搞挂时，也是靠断电重进恢复的。
4. **SELinux 是 Permissive**：这为后面的临时 root 和调试省了很多事。
5. **平台签名是公开的 AOSP testkey**：这一点很离谱，后面单独讲。

分区映射（通过 `/dev/block/platform/.../by-name` 确认）：

```text
boot      -> mmcblk0p7
recovery  -> mmcblk0p8
system    -> mmcblk0p20
cache     -> mmcblk0p21
userdata  -> mmcblk0p22
nvdata    -> mmcblk0p18
...
```

注意：设备里自带的 `/vendor/etc/recovery.fstab` 和实际分区对不上，像是套用了别的模板。**不要相信杂牌固件里的 fstab**，要以 `/proc/partitions` 和 by-name 为准。

## 2. 第一关：第三方应用死活装不上

### 2.1 症状

从设备里已导入的 EpubReader APK 开始测试：

```bash
pm install -r /data/local/tmp/epub.apk
# Failure [INSTALL_FAILED_INVALID_INSTALL_LOCATION]
```

但奇怪的是：

- 预装的酷狗更新它的 APK：**成功**
- 预装的 Remix MyPlayer 更新：**失败**
- 任何全新包名：**全部失败**
- `settings get secure install_non_market_apps`：已经是 `1`
- 改 `default_install_location=1`、`pm install -f`：都没用

所以这不是“未知来源”开关，也不是存储空间不足。`INVALID_INSTALL_LOCATION` 这个错误码把我一度带向“SD 卡/安装位置”的方向，但后来证明它只是厂商补丁返回的一个很有误导性的错误。

### 2.2 发现 `ignore_app`

把全局设置全量拉出来：

```bash
settings list global | grep -iE 'install|ignore|app'
```

看到两个很可疑的键：

```text
ignore_app=com.kugou.android.lite,com.eusoft.eudic,com.tencent.qqmusiccar,com.netease.cloudmusic,com.netease.cloudmusic.watch,com.ximalaya.ting.android
set_install_location=0
```

酷狗恰好就在 `ignore_app` 里。于是试着把 EpubReader 的包名加进去：

```bash
settings put global ignore_app "$(settings get global ignore_app),com.wirelessalien.compact.epubreader"
pm install -r /data/local/tmp/epub.apk
# Success
```

**装上了。**

再验证一下：把不在名单里的 Remix 更新，仍然失败。  
所以 `ignore_app` 就是厂商的新包安装白名单/豁免表。

但这不是“漏洞”，只是厂商留的一个土办法。我们继续往代码层看。

### 2.3 找到 system uid 的厂商管理应用

`pm list packages` 里有一个非常显眼的包：

```text
bs.android.systemcontrol  ->  /vendor/operator/app/SystemControl/SystemControl.apk
```

它的权限和组件很“管理端”：

- `userId=1000`，和 `android.uid.system` 共享 UID
- 设备管理员（Device Admin）
- 辅助功能服务（AccessibilityService）
- 监听 `PACKAGE_ADDED / PACKAGE_REMOVED / PACKAGE_REPLACED`
- 有 `INSTALL_PACKAGES`、`WRITE_SECURE_SETTINGS`、`KILL_BACKGROUND_PROCESSES` 等权限
- 内部还有 Room 数据库 `app_info`、`internet_time_limits`、`time_lock_settings`
- 代码里能看到 `PasswordLockActivity`、`persist.sys.install.by.pwd`、`getLockPassword/setPassword`

这基本就是一套“应用管控/家长控制/远程管理”的杂牌 MDM。它很可能就是安装密码和前台监控的幕后黑手。

### 2.4 真正的开关：`persist.sys.install.by.pwd`

一开始看到这个属性是空的：

```bash
getprop persist.sys.install.by.pwd
# (空)
```

试着设成 `0`，还是装不上；设成 `1`，再去装新包：

```bash
setprop persist.sys.install.by.pwd 1
pm install -r /data/local/tmp/testapp2.apk
# 这次错误变成 INSTALL_FAILED_INVALID_APK: code is missing
```

错误从“安装位置非法”变成了“APK 没有代码”，说明**安装位置检查已经过了**。换一个带 `classes.dex` 的正常测试 APK：

```bash
pm install -r /data/local/tmp/testapp3.apk
# Success
```

`testapp3` 不在 `ignore_app` 里，也不是平台签名，纯第三方包。  
**安装限制被绕过了。**

### 2.5 代码级确认

从设备拉出 `services.odex`，解出里面的 dex，反汇编 `PackageManagerShellCommand.runInstall`，能看到类似逻辑：

```text
const-string/jumbo v1, "persist.sys.install.by.pwd"
invoke-static {v1, v4}, Landroid/os/SystemProperties;.getInt:(Ljava/lang/String;I)I

if (值为 0) {
    // 放弃安装会话
    doAbandonSession(...)
    return
}

// 非 0
doCommitSession(...)
return
```

附近还能看到 `ignore_app` 字符串和厂商的日志 tag `hqb`。  
这解释了所有现象：

- 新包安装走 shell 命令时，厂商补丁读 `persist.sys.install.by.pwd`
- 默认空/0 → 放弃 → 上层报一个很误导的 `INVALID_INSTALL_LOCATION`
- 设成 1 → 提交 → 正常安装
- `ignore_app` 是更早发现的白名单旁路，不是唯一的开关

> 顺带一提：`set_install_location` 是另一个诱饵键，改了它并不会解决这个问题。

### 2.6 处置

最终做了两件事：

```bash
setprop persist.sys.install.by.pwd 1
settings put secure enabled_accessibility_services ""
settings put secure accessibility_enabled 0
pm disable-user --user 0 bs.android.systemcontrol
```

- `pm disable-user` 把厂商管理应用禁用为 `disabled-user`
- 关闭它的辅助功能
- 它原来挂着的设备管理员也不再处于启用列表

然后分别用 **ADB `pm install`** 和 **设备本机 PackageInstaller UI** 安装不在白名单里的新包，全部成功；重启后设置仍然有效。

## 3. Root 路线选择：三条路，最后选了 Magisk

设备没有官方固件、没有 TWRP、没有可靠 recovery，所以“先备份、再动 boot”是底线。可用的路线大致三条：

1. **AOSP platform testkey → system uid 辅助应用**  
   设备系统应用是用公开的 AOSP testkey 签名的，理论上可以自己签一个 `sharedUserId=android.uid.system` 的应用，直接以 system uid 运行。
2. **mtk-su（CVE-2020-0069）→ 临时 root**  
   MTK 命令队列驱动的老漏洞，arm64 版本在这台 Android 7 + 3.18 内核上仍然可用，拿 `uid=0`。
3. **Magisk boot 补丁 + fastboot → 永久 root**  
   有 stock boot 备份、BL 已解锁，只要能进 fastboot、能安全回滚，就是最标准的永久方案。

实际顺序是：先用 mtk-su 拿临时 root 做备份，再回头评估 testkey，最后用 Magisk 做永久 root。

## 4. AOSP testkey：一个不该出现在量产机上的错误

### 4.1 发现

检查系统应用签名：

```bash
apksigner verify --print-certs Settings.apk
apksigner verify --print-certs SystemControl.apk
```

结果它们都是：

```text
DN: EMAILADDRESS=android@android.com, CN=Android, OU=Android, O=Android,
    L=Mountain View, ST=California, C=US
SHA-256: c8a2e9bccf597c2fb6dc66bee293fc13f2fc47ec77bc6b2b0d52c11f51192ab8
```

这正是 **AOSP 平台测试密钥（platform testkey）** 的证书，私钥是公开的。

也就是说，这台设备虽然 `ro.build.tags=release-keys`，但系统应用实际上是用公开 testkey 签的。

### 4.2 它意味着什么

Android 的 `sharedUserId` 机制允许一个应用声明与系统共享 UID：

```xml
<manifest package="com.example.helper"
    android:sharedUserId="android.uid.system">
    ...
</manifest>
```

只要这个 APK 的签名和现有 `android.uid.system` 的签名一致，安装后就会得到 **uid 1000（system）**。因为平台私钥是公开的，所以任何能在这台设备上安装 APK 的人，都可以签出这样的应用。

### 4.3 复现步骤（仅限自己的设备）

1. 从 AOSP 获取公开的 `platform.pk8` / `platform.x509.pem`（这就是设备的平台证书对应的私钥）。
2. 写一个最小 APK，声明 `android:sharedUserId="android.uid.system"`。
3. 用平台密钥签名：

```bash
apksigner sign --key platform.pk8 --cert platform.x509.pem --out syshelper.apk aligned.apk
```

4. 通过前面解开的安装限制安装它。
5. 检查：

```bash
dumpsys package com.example.helper | grep userId
# userId=1000
```

6. 它的 Activity 以 system uid 运行，可以执行系统级命令、读取 system 组可读的块设备等。

我确实构建并安装了一个 `SysHelper` 来验证这条路，`dumpsys` 显示 `userId=1000`，能够以 system 权限运行命令。**但它不是最终的 root 方案**：system uid 还不是 root，而且一个导出的、能执行任意命令的 system uid 应用本身就是后门。验证完就卸载了，只保留了 APK 和 testkey 作为研究材料。

### 4.4 为什么这是严重问题

- 平台签名私钥公开，意味着任何本地安装能力都能伪造 system uid 应用。
- 系统应用、`android.uid.system` 的共享 UID、设备管理权限全部失去信任边界。
- 这不是“用户能 root”这么简单，而是 **任何恶意 APK 都可能拿到 system uid**。
- 对厂商来说，这是典型的“用 testkey 出货”事故；对用户来说，这是设备安全的根子上就有洞。

> 这段只是设备特定的安全分析。不要拿公开 testkey 去签任何面向他人的 APK；也不要在别人的设备上复现。

## 5. mtk-su：临时 root 的具体用法

### 5.1 漏洞背景

`mtk-su` 利用的是 MediaTek 命令队列驱动的老漏洞 **CVE-2020-0069**。大意是：

- MTK 的 `mtk_cmdq` 驱动对 ioctl 的权限检查不严
- 本地进程可以通过它读写内核内存
- 配合 `/proc/kallsyms` / 符号表定位 `init_task`、当前 `task_struct`
- 修改当前进程的 `cred`，把 uid/gid 提升到 0
- 设备 SELinux 是 Permissive，所以没有额外的策略阻挡

这台设备：

- 内核 `3.18.35`
- Android 安全补丁级别 `2019-05-05`
- CVE-2020-0069 的修复在 2020 年 3 月之后
- 厂商 2025 年重建系统，但显然没有补这个洞

于是 mtk-su 直接工作。

### 5.2 运行

把 arm64 的 mtk-su 推到设备：

```bash
adb push mtk-su /data/local/tmp/
adb shell chmod 755 /data/local/tmp/mtk-su
```

直接执行：

```bash
adb shell /data/local/tmp/mtk-su -v -c id
```

输出会经历：

```text
Temporary root by diplomatic@XDA
...
Building symbol table
kallsyms_...
Patching credentials
...
UID: 0  cap: 3fffffffff  selinux: permissive
```

最终拿到 `uid=0`。

注意：`-c` 后面跟的是**单个可执行命令/参数**，不是 shell 字符串。要执行多行脚本，用 stdin：

```bash
adb shell "cat /data/local/tmp/root_script.sh | /data/local/tmp/mtk-su -v"
```

这也是后来备份脚本的用法。

### 5.3 作用与限制

- **临时 root**：只对当前 mtk-su 启动的那个 root 进程/子进程有效
- 不会修改 boot 分区，不会留下持久 root
- 重启后需要重新运行
- 设备安全补丁一旦真的补上 CVE，方法就失效
- 二进制来自公开工具，运行时本身是对内核的利用，存在崩溃风险

在这台设备上它稳定工作，所以被用作“先拿权限做备份”的跳板。

## 6. 把系统备份下来，再谈刷机

在没有任何官方固件的情况下，**备份比 root 更重要**。用 mtk-su 的 root 权限只读 dump：

```bash
dd if=/dev/block/mmcblk0p7  of=/data/local/tmp/backup/boot.img
dd if=/dev/block/mmcblk0p8  of=/data/local/tmp/backup/recovery.img
dd if=/dev/block/mmcblk0p20 of=/data/local/tmp/backup/system.img
dd if=/dev/block/mmcblk0p1  of=/data/local/tmp/backup/proinfo.img
dd if=/dev/block/mmcblk0p2  of=/data/local/tmp/backup/nvram.img
...
dd if=/dev/block/mmcblk0    of=/data/local/tmp/backup/emmc_head8m.img bs=4096 count=2048
```

拉回 PC 后校验：

- `boot.img`（16MB）：`c2d63d3733a1ada193664dacdbed21a3`
- `recovery.img`（16MB）：`167cb225053c7236531b18a4c949cc76`
- `system.img`（2.5GB）：`1f6c8ff71ff844791f38565c063b068a`
- `emmc_head8m.img`（8MB）：`fcefa06a6eedd45db272e3f9be94d4b4`
- `boot0/boot1`（4MB）、`nvram`、`nvdata`、`lk`、`seccfg`、`protect1/2`、`proinfo`、`logo`、`expdb`、`frp`、`metadata`、`keystore`、`tee1/2`、`secro`、`para`、`oemkeystore`、`flashinfo`：见 `MD5SUMS`

另外还备份了：

- `SystemControl_data/`：厂商管理应用的数据库/MMKV
- 修改前的 `settings_global.txt`、`settings_secure.txt`、`device_policy.txt`

**重要的认知：整分区 dump 不等于可直接刷的镜像。**

`boot.img` 是 16MB 的整个 boot 分区，里面除了真正的 Android boot image，还有大量尾部填充和 AVB 信息。后来正是这个“整分区镜像”把 fastboot 坑了。

## 7. Magisk 永久 root：LK 的 16MB 大坑

### 7.1 打补丁

用 Magisk v26.4（Android 7 比较稳的版本）的官方 `boot_patch.sh`，配合从 APK 里提取的 arm64 二进制：

```bash
# 目录里包含 boot_patch.sh / util_functions.sh / magiskboot / magiskinit /
# magisk64 / magisk32 / magiskpolicy / busybox / stub.apk
KEEPVERITY=true KEEPFORCEENCRYPT=true BOOTMODE=true \
  sh boot_patch.sh boot.img
```

补丁过程会：

- 解析 stock boot
- 检查 ramdisk 状态
- 把 `magiskinit` 作为新的 `/init`
- 加入 `overlay.d/sbin/magisk32.xz`、`magisk64.xz`、`stub.xz`
- 保留 verity/forceencrypt
- repack 成 `new-boot.img`

输出显示：

```text
HEADER_VER [0]
KERNEL_SZ  [6409670]
RAMDISK_SZ [2877518]
OS_VERSION [7.0.0]
KERNEL_FMT [gzip]
RAMDISK_FMT [gzip]
AVB1_SIGNED
Repack to boot image: [new-boot.img]
```

生成的 `new-boot.img` 仍然是 **16MB**（因为输入是整分区 boot 镜像）。

### 7.2 fastboot 驱动先出事

一开始 `fastboot devices` 什么都看不到，但 Windows 的 PnP 里有：

```text
Status: Error
FriendlyName: Android
InstanceId: USB\VID_0BB4&PID_0C01\0123456789ABCDEF
```

设备其实在 fastboot，只是 **Windows 的 Google USB 驱动丢了**。新旧 fastboot 都一样看不到。

- 重新装回 Google 驱动后，PnP 变成 `Android Bootloader Interface / OK`
- `fastboot devices` 正常显示设备
- 这跟 fastboot 版本无关

### 7.3 16MB 整分区镜像导致 no link

驱动修好后，尝试：

```bash
fastboot boot boot_magisk.img
# Sending 'boot.img' (16384 KB)
# FAILED (Write to device failed in SendBuffer() (no link))
```

换 stock 16MB 镜像也一样：

```bash
fastboot boot boot_stock.img
# 同样 no link
```

再试 `fastboot flash boot boot_magisk.img`：

```bash
# Warning: skip copying boot image avb footer
# (boot partition size: 0, boot image size: 16777216)
# Sending 'boot' (16384 KB) ... FAILED (no link)
```

**没有写入 boot**：失败发生在发送阶段，bootloader 还没拿到完整镜像，更没执行写分区。  
但 fastboot 服务被搞挂了，后续连 `getvar`、`reboot` 都 no link，只能断电重启恢复。

关键信息：

```bash
fastboot getvar max-download-size
# max-download-size: 0x8000000  (128MB)
```

最大下载大小足够，所以不是 `max-download-size` 的限制；问题是 **16MB 的整分区 boot 镜像**（含尾部 AVB/填充）在这台 LK 上触发了 no-link。`boot partition size: 0` 的警告也说明 bootloader 对分区的报告有毛病。

### 7.4 用 trimmed 镜像解决

按 boot header 计算真实长度：

- header 1 页（2048）
- kernel 页
- ramdisk 页
- DTB 页

## 9. 安全清理与经验教训

### 9.1 清理

- 卸载了用于验证 testkey 的 system uid 辅助应用（不能留一个能执行任意系统命令的导出组件）
- 卸载了测试 APK
- 关闭了临时局域网 HTTP 文件服务
- 保留了 `mtk-su` + `root.sh` 作为 Magisk 异常时的应急 root
- 保留了 stock boot/system/关键分区备份和哈希

### 9.2 经验

1. **不要被 `INVALID_INSTALL_LOCATION` 带去查 SD 卡**：厂商补丁可能只是拿这个错误码当“安装被拒绝”的通用错误；确认存储类型要看 `/proc/partitions`、`/sys/block`、`mmcblk0boot0/rpmb`，这台就是 eMMC。
2. **不要相信杂牌固件里的 fstab**：它可能和真实分区完全对不上。
3. **先备份，再写分区**：没有官方固件时，full boot/system dump 就是生命线。
4. **整分区 dump ≠ 可刷镜像**：16MB boot 分区里只有前 9MB 左右是 boot image；尾部 AVB/填充会让 LK 的 USB fastboot 挂死。用 trimmed 镜像。
5. **fastboot 看不到设备先查驱动**：PnP 状态 Error/Android + VID_0BB4&PID_0C01 就是典型；不是命令行版本问题。
6. **公开 testkey 是供应链级问题**：系统应用用 AOSP testkey 签名，让 system uid 应用可被任意签名；这不是“root 漏洞”，而是设备信任根坏了。
7. **mtk-su 是临时 root 的好工具，但不是永久方案**：CVE-2020-0069 在老 MTK 上很好用，重启即失效；最终持久化还是 Magisk boot。
8. **厂商安装限制要往代码层看**：`ignore_app` 是表象，`PackageManagerShellCommand.runInstall` 里的 `persist.sys.install.by.pwd` 才是开关。
9. **SELinux permissive 是双刃剑**：调试/root 方便，但也意味着系统本身的安全边界很弱。
10. **Android 7 已老**：root 后能装第三方应用，但现代应用的兼容性、Zygisk 等会有限制。
